# DECISIONS.md

Deviations from the OKF store v1 design (ledger, parse, merge, sync, profiles), recorded with the section they affect. **Search and retrieval are specified in `docs/SEARCH.md`** — not listed here as deltas. Each entry states what the OKF design expects, what this build does, and why.

## §5 Data model

- **`reason` on `Change`.** The spec puts the retract/erase reason code only in the tombstone. This build adds an optional `reason` enum to every change (and a `reason TEXT` column on `changes`) so a retraction's reason code is in the ledger without free text. It is metadata (an enum), so it is covered by the digest (§10.3).
- **Frontmatter payloads.** The spec lists `frontmatter_key` and `frontmatter_value` as separate payload kinds. A change has one payload, so this build stores one `frontmatter_entry` payload `{key, raw}` under the concept scope. `Target::FrontmatterKey.key_commit` is still the keyed commitment to the key name under the concept's `K_com`.
- **Asset payloads** carry `u32 path_len | path | bytes` so `create_asset` is one payload (the spec names `asset_bytes` and `path` separately).
- **`SectionPayload`** stores the raw heading line(s) without the anchor in addition to the heading text, so setext headings, closing `#` sequences, and CRLF render back byte-for-byte (I3).

## §6.1 Ledger schema

- `target`, `inputs`, `valid`, `lineage`, `origin` are stored as JSON in the BLOB columns rather than canonical CBOR. The digest still uses canonical CBOR (RFC 8949 §4.2.1); the storage encoding is not covered by any integrity guarantee and JSON kept the decoder out of scope.
- One bookkeeping table was added: `erasure_markers (section, concept, after_section, reason)`, so a rebuilt hot tier can render an erased section's marker at its former position (§13.1).

## §6.2 Hot schema

- Additional columns/tables: `state_concepts.gen_actor / gen_at / content_version` (the inputs to the managed `generated` and `verified` keys, maintained on apply), `state_sections.heading_line`, `state_retracted`, `state_verified`, `state_erased_markers`. All are pure functions of the ledger (I13) and are checked by `hot check` through a logical dump comparison.
- `state_concepts.status` stores `unset` when `set_status` was never applied, so the renderer can omit the key (OKF reads absence as `stable`).

## §6.3 Reads and writes

- **Async cold payload flush.** After a successful commit, ciphertext stays in `staged_payloads` and a background thread drains to `.wisp/payloads/` (readers still use staged-first). `Repository::flush_cold_payloads`, `Repository::drop`, and `open` recovery flush before sync/export barriers. Backpressure: when staged ciphertext exceeds `WISP_MAX_STAGED_PAYLOAD_BYTES` (default 128 MiB), the commit path blocks with a synchronous drain. Power-loss immediately after commit may leave payloads staged until the next `open` (I25).
- **Commit order inside the critical section.** The spec commits the ledger, then the hot tier. This build commits the hot tier first, then the ledger, both while holding the ledger write lock. Reason: with ledger-first, a writer acquiring the lock between the two commits sees a head whose changes are not yet in the tier and would wrongly conclude the tier is stale. If a process dies between the commits the tier is ahead of the ledger; `Repository::hot` sees an unknown head and rebuilds.
- **Rebuild holds the ledger write lock.** A rebuild computed from a stale head could otherwise be committed over a newer tier state.
- Built-in search indexes live in each ref’s `hot.db` under `cache/refs/` (`docs/SEARCH.md`). Token rollup DBs are not fully materialized; `pack` uses `tok:approx:chars4`.

## §7.2 Frontmatter CST

- Entries are split by a line-structured scanner (column-0 `key:` starts an entry; indented lines, `- ` items, multi-line flow collections and block scalars continue it; comments directly above an entry attach to it) instead of a `tree-sitter-yaml` CST. Values are parsed with `serde_yaml` only for comparison. Separator spans between entries are folded into the preceding entry's raw span on record, so untouched frontmatter round-trips byte-for-byte (I3) while the hot tier keeps one row per entry.
- A top level that is not a block mapping is stored as one opaque span and reported as non-conformant; this build does not yet rewrite it in block style on a managed-key write (the file is refused unless `--allow-nonconformant`).

## §7.4 Concept identity

- Rule 3 (no `wisp_id` = new concept) has one pragmatic exception: a file **without** a `wisp_id` at the path of a known concept, when no other file carries that concept's ID, is treated as that concept (reported as a repair). Without this, a model that strips the identity line produces a path conflict against the concept it was editing.

## §7.5 Section identity

- The preamble is identified by position: there is exactly one per concept, so an unanchored preamble reattaches to the prior preamble before rule 6 runs.
- Split (rule 6): the spec compares P's previous body to "P's new body followed by this section's heading line and body". This build accepts that form **or** the form without the heading line, since inserting a new heading into existing prose is the common split and the heading text never existed in the old body.
- Normalization trims trailing whitespace per line, normalizes line endings, and collapses trailing blank lines to one line break before comparison.

## §8 Operations

- `set_status` carries the status as a small encrypted payload (kind `status`) rather than in metadata.
- Editing `generated` or `verified` by hand is ignored silently (the spec says "a refusal otherwise"); `sources` and `status` edits map to `source_put`/`source_remove`/`set_status` as specified.
- Link rewriting on move is performed by `wisp mv` (as `update_section` changes in the same changeset). An OS rename recorded by `wisp record` produces `move` and an alias but does not rewrite inbound links.

## §9 Record pipeline

- Change detection records a SHA-256 of the bytes wisp last wrote in `checkout.idx`, so an mtime-only touch is not an edit and a concurrent rewrite is detected by content.
- **Section logging patches.** `append_section` / `prepend_section` store a fragment payload and stitch onto the hot body without a section-version precondition (headless). `update_section` remains the default full replace with optimistic concurrency. Ref merge treats divergent patch-only chains on the same section as compatible (replay both). See `docs/APPLY.md` and **`docs/AGENT-WRITERS.md`**.
- **Delta materialize (async).** After a commit, wisp enqueues a **publish set** derived from the changeset and drains it on a manifest heartbeat (`[materialize]`, default `tick_ms = 250`). Only dirty concept paths, assets, and affected directory views are rendered from hot (`publish_ref_delta`); unrecorded edits on disk are not overwritten. `record` and `headless` share this path. Full-tree render is reserved for `checkout`, `switch`, erase recovery, and explicit barriers (`wisp materialize --wait`, sync/pack, `Repository::drop`). See `docs/WORKTREE.md`.
- A working-tree advisory lock (`.wisp/worktree.lock`, a SQLite `BEGIN IMMEDIATE`) serializes tree rewrites across processes.

## §10.1 Keys

- The default master-key source is a key file at `.wisp/keys/master.key` (mode 0600) instead of the OS keychain. `WISP_MASTER_KEY` and `--passphrase` (Argon2id with the specified parameters) work as specified. A keystore check value detects a wrong master key early (exit 9).
- Ed25519 signing: `wisp actor gen-key` generates a keypair, stores the seed at `.wisp/keys/signing/<actor>.seed` (or use `WISP_SIGNING_SEED` in CI), and registers the public key; `wisp actor key` still registers an external public key only. Commits sign the changeset digest when a matching local seed exists. `fsck` verifies signatures when the actor’s public key payload is present.

## §10.4 Erasure groups

- Group creation inserts the `groups` row directly (mutable bookkeeping) rather than through a change; membership goes through `group_add`/`group_remove` changes as specified.

## §10.5 Erase procedure

- The erase change is committed through the normal optimistic commit, and the tombstone, scope flags, payload-absence flags, and marker positions are written in a second ledger transaction immediately after. On `Repository::open`, `finish_erase_bookkeeping` completes that second transaction when an `Op::Erase` change has no tombstone row yet; then `recover` shreds and rewrites managed worktrees. See `docs/ERASE.md`.
- Phase 1 purges search-derived rows in hot.db (FTS, trigram, RI, dense embeddings) for erased sections, then hot tier state; section scopes also delete the ledger’s section id in hot before scope-column purge. Token DB purge follows the same pattern when present.
- After shred, every managed checkout (primary and linked worktrees) is re-rendered; `wisp erase --discard` may overwrite unrecorded edits in those trees. A ledger `erase_rewrite_pending` flag survives a crash between shred and rewrite; `recover` on open clears it after rewriting. Erase returns an error unless every affected scope is shredded and none are pending shred.

## §11 Concurrency

- Linked worktrees (§11.4) are implemented minimally: `worktree add|list|remove`, checkout under `.wisp/worktrees/<name>/` (or `--path`) with `.wisp-checkout.idx`, ledger `worktrees` bookkeeping, and one ref per checkout. Merge (§11.5): fast-forward, divergent replay with a two-parent merge node, scope-key conflict detection (including same-commitment no-conflict, erase-wins with skip replay, retract-vs-content), **per-scope change chains** on conflict rows (`into_changes` / `source_changes`) so `--resolutions` skips all losing-side edits on that key (not only the tip change), layered changeset ordering for hot rebuild (`base` → `into` tip → `source` tip, **recursive expansion** of nested two-parent changesets via `changesets_since` + `ordered_changeset_ids`), `--resolutions` JSON (`take`: `ours`|`theirs` per conflict), `--abort` clears `.wisp/merge.json`; resolved merges and erase-wins persist skip lists in the ledger `merge_replay_skips` table (and optionally `cache/refs/<ref>/merge-skip.json` for backward compatibility) for hot rebuild/check (skip metadata is found by walking `based_on` from the ref head). Concept path moves use `wisp mv` (not headless `move`). Duplicate paths are refused at commit (`PathFree`). Integration coverage: `merge_playbook`, `contrib/merge-rules/cases.toml`, and `merge_rules` in `wisp-invariants` (see `docs/MERGE.md`). Sync (§11.6): `file://` push/pull, dumb HTTPS pack at `{remote}/wisp/v1/pack.zst`, SSH via `rsync` + local transport, and stdio Hello/Ack (`wisp serve --stdio`). See `docs/EXTENSIONS.md`. Trusted `file://` transfer copies missing wrapped scope keys from the source (same master key), reconciles `erased`/`shredded` flags for scopes that already exist on the destination, cold-shreds and deletes keystore rows when the source has shredded, then runs erase recovery on the destination. HTTP packs omit `keys/` unless `WISP_PACK_INCLUDE_KEYS=1`; optional `WISP_HTTP_TOKEN` requires a Bearer token on pack GET/PUT. Incremental sync does not merge unrelated master keys. Branches, `switch`, headless writes, `apply` batches, read assertions, and `--assert-head` are implemented as specified.
- `--base any` is honored for headless operations; a policy rule with `unconditional = true` can deny it.

## §12 Profiles

- The okf-0.1 profile and the 0.1→0.2 migration plan (timestamp → `generated` with origin; `Citations` → sources) are implemented; down-export via `checkout --profile 0.1` / `export --profile 0.1` (to `--to` only on the primary worktree) is implemented.

## §13 Views and git interop

- Erasure markers for a section whose preceding section no longer exists are rendered after the preamble; for a concept with no sections left they follow the frontmatter.
- `export --archive` writes a `.tar.zst` of the rendered bundle. `export --git` renders and runs `git init` + one commit. `import --git` defaults to a **snapshot** (`git archive` + one `record`; `--squash` sets the message). `import --git --history` replays commits oldest-first (one wisp changeset per non-empty tree) and writes `meta/git-map.json` (git SHA → wisp changeset). `import <dir>` copies a plain bundle into the working tree and records it.

## §14–§16 Feed, search, CLI

- **Search:** `docs/SEARCH.md`. **Extensions:** `docs/EXTENSIONS.md`.
- **Token codecs:** `wisp pack` / `wisp tokens` resolve `manifest.toml` `codecs.default_tokenizer` through `wisp-sub-tokens::TokenCodec`. Community builds ship `tok:approx:chars4` and `tok:approx:bytes4` only; other `tok:*` ids require a product subscriber (`docs/EXTENSIONS.md`).
- **Stdio sync:** `Hello.transport=cold_pack` + PushRef pushes ColdPack after Ack; `cold_pack_pull` + PullRef sends ColdPack from the server after Ack; `local_path` (default) keeps the legacy third-line path. Not MCP.
- **Search IR battery:** `contrib/search-battery/cases.toml` only.
- Erase targets an actor with `--actor-id <actor>` (the global `--actor` names the acting identity).
- `record --resolve` clears `.wisp/merge.json` after a successful record on the merge target ref; finish the merge with `wisp merge <source> <into> --resolutions <file>`.
- `wisp diff --from/--to` compares section-level ops along the `based_on` chain between two changesets; `diff` without those flags compares the working tree with its base.

## §5 / §11.3 Derivation inputs and `wisp impact`

- **Pinned inputs.** `--input <path>#<section>@<changeset>` records `InputRef::Concept.at`, the snapshot the writer read (agents pass `head` from `wisp cat --json`). The pin is validated before commit: the changeset must exist, and the section must exist at that snapshot under the concept the path resolves to now. A section version (`ChangeId`) passed in place of a snapshot is rejected with a hint, since both are ULIDs. The same validation now applies to `at` in `wisp apply` batches, which used to be stored unchecked: an unverifiable pin would be false evidence for impact tracing. When no `@<changeset>` is given, `at` stays absent; the read snapshot is never inferred from the head at commit time. `at` already existed in the model and is encoded with `opt`, so records without it hash exactly as before.
- **Stricter `--input` parsing.** A section id that does not parse used to be dropped silently, turning a section input into a whole-concept input. It is now a usage error (exit 2). The `@` suffix is only recognized after `#<section>`; a pinned whole-concept input is available in batches only, because paths may contain `@`.
- **Missing-inputs warning.** When an actor that is not `human:*` writes section content (`add_section`, `update_section`, `split`) with no declared inputs, the result carries `warnings: [{code: "no_declared_inputs", actor, sections, message}]` (headless writes and `apply`: a `warnings` key present only when non-empty; `record`: appended to its existing `warnings`). It is never a refusal: original observations and formatting edits have no source. It checks that inputs were declared, not that they are complete.
- **Per-op inputs in `apply`.** `ApplyOp` accepts an optional `inputs` list that replaces the batch-level `inputs` for that op's content changes (an explicit `[]` declares none). Batch-level inputs remain the default, so existing batches behave as before. Previously every content change in a batch received every batch input, over-attributing dependencies in multi-op batches. Format: `docs/APPLY.md`.
- **`inputs_complete` (`--inputs-complete`).** A new optional `Change.inputs_complete` flag declares that a change's inputs are its complete dependency set, so the new version does not inherit the previous version's dependencies (a full rewrite, a different actor, or a partial input list never clears them on their own). It is part of the hashed change metadata, encoded only when true, so every existing record encodes and verifies exactly as before; it is stored in a new nullable `changes.inputs_complete` column, added on open to ledgers from earlier builds (an `ALTER TABLE … ADD COLUMN`, which updates no row). **Compatibility:** see the format marker below. `wisp why` shows `inputs_complete: true` on such events.
- **`wisp impact` (historical mode only).** `wisp impact <path|concept-id>[#section] [--depth N] [--ref R]` walks forward from a source. Edges: declared inputs (`pinned` when the input's `at` shows exactly the affected version, `unversioned` when the affected version is merely earlier in the writer's history), `inherited` (a later version of the same section whose predecessor is affected, unless it declared `inputs_complete`), and `split` / `merge` / `copy` lineage (the child inherits the parent's dependencies; a merge the union; cut by `inputs_complete`). A pin that shows a version from before the dependency existed rules the writer out. Results are change versions reachable from the ref head; intermediates reached through an explicit pin into another branch may appear in `via` but are never results, and dependents are never joined across unrelated branches. Changes resolved away by a merge are reported with `merge_skipped: true`. Results are deduplicated by version (cycles terminate); `via` is one shortest path, source first. `--depth` (default 3) counts dependency hops; `inherited` hops do not count, so a run of small edits to one section does not exhaust the limit. `truncated` is true only when an unexplored dependency exists beyond the limit. Only `InputRef::Concept` inputs and section lineage are followed (asset and `Source` inputs are not). A concept's frontmatter (`create`, `set_key`, `unset_key`, `source_put`, `source_remove`, `set_status`) is one unit with the same rule as a section: each frontmatter version inherits from the previous one unless it declares `inputs_complete`; such results carry `kind: "frontmatter"` (sections `"section"`, other concept-level changes `"concept"`). A whole-concept input matches every unit of the concept.
- **Departures from the proposal's output.** No `--mode` flag (only historical exists; `data.mode` is always `"historical"`), no `classification`, and `unresolved_dependencies` is replaced by `unversioned_links` (results whose own edge is unversioned; in historical mode they are included, not unresolved). Added: `source.state` (`live`, `retracted`, `removed`, `erased`, `not_on_ref`), `head`, per-result `link`, `actor_id`, `merge_skipped`, `inputs_complete`, and `untracked_content_changes` (section writes on the ref with no declared inputs), so an empty or short answer is never read as "nothing was affected". The `--assert`-to-snapshot conversion in the proposal is not built; pins come from `@<changeset>` only.
- **Labels after erasure.** Starting points resolve by path on the ref (live or retracted) or by opaque concept id from ledger metadata. No payload is read: paths come from the ref's hot tier only and are `null` once erased or gone; actors use the existing display, which falls back to `process:erased-…`; ids are always present. `wisp impact` never writes; opening a repository may complete a pending erase, and reading a ref may rebuild its hot tier (both pre-existing behavior for every command).
- **`wisp why` is ref-scoped.** `why` lists only changes reachable from the selected ref (default: the ref checked out in the working tree), including when it recurses into inputs, matching `wisp impact`. It used to scan the whole ledger regardless of branch. Behavior change, noted in `CHANGELOG.md`.
- **`wisp retract` reports dependents.** The result adds `concept`, `flagged` (concept ids of recorded direct dependents on the ref, computed by the `wisp impact` walk at depth 1 after the retraction, read-only), and `flagged_truncated` (more dependents exist beyond one hop; run `wisp impact`). `wisp erase` is deliberately broader: see below.
- **Format marker for `inputs_complete`.** `manifest.toml` `repo.format` becomes `2` the first time a change records `inputs_complete` (before that change is written), never on upgrade, so repositories that never use the flag stay at `1` and readable by older builds. Trusted sync raises the destination's format to the source's. This build refuses any `repo.format` above `2` with exit 4 and "this repository uses a newer format; upgrade wisp" (`details.code: "format_too_new"`) instead of reporting damage. **Limitation:** 0.1.0 binaries never read `repo.format`, so they cannot honor the marker: on a format-2 repository they still open it and their `fsck` reports digest mismatches for the flagged changesets. The refusal protects every build from this one onward. Making 0.1.0 itself refuse would need a manifest change it cannot parse (for example a different type for an existing key), which is a breaking hack and was not done.
- **Identical-content merges carry the union.** A byte-identical edit to the same section on both sides of a merge is not a conflict, so both versions survive and neither is skipped. Snapshot resolution returns every concurrent head of a unit; a reader pinned after the merge depends on both, and the next version inherits both dependency sets (the same union rule as `merged_from`). Elsewhere a unit has exactly one head.
- **`wisp erase` reports dependents everywhere.** Erasure destroys the key for every branch, so erase (its preview and its result) runs the impact walk from each erased concept or section on **every** ref, to the default depth, metadata only (it also runs during open-time erase recovery). The result adds `dependents_by_ref` (ref → `[{concept_id, section_id, kind, version, depth, link, source_concept_id, source_section_id}]`, refs with none omitted) and `dependents_truncated`; `flagged` (stored in the tombstone) becomes the union of dependent concepts across refs. It replaces the old one-hop, concept-level scan of the whole ledger. `wisp impact` stays ref-scoped by default.
- **Retention of opaque ids.** Input references, change targets, and scope rows are insert-only and covered by the digest, so the random, non-content-derived ids of erased concepts and sections remain after erasure and impact traces through them. An id carries no content, but it is linkable: anything that recorded it while labels were visible (a saved `wisp impact --json`, a log, a ticket) can connect it back to the erased item. Treat saved impact output like other plaintext exports (`docs/TRUST-BOUNDARY.md`).
- **Not in this version.** URL inputs: `InputRef::Source` exists but nothing constructs it, so a bad web page cannot yet be a starting point; it is the next most valuable addition. Current mode waits on testing of the replacement semantics above. The visual report is planned as a separate `contrib/` script that reads `wisp impact --json`, not as part of the core binary.
- **Performance.** The walk reads every change that declares inputs or lineage once, then resolves ancestry lazily (a seq-pruned search, memoized) and memoizes unit-at-snapshot lookups. A debug-build probe (`impact_scaling_probe`, ignored by default: 40 notes × 25 rounds, 1,000 chained writes) takes about 0.3 s at depth 3 and 3.7 s for all 1,000 results; release builds are much faster, but the cost still grows faster than linearly with history because each pinned snapshot and each inheritance check resolves heads. If that matters at scale, the next step is a rebuildable input-edge and unit-head index in the hot tier.

## HTML export (`wisp export --html`)

- **Consistent view (Part 1).** Export holds the advisory `worktree.lock` for collect → render → publish rename → `exports` registration, refuses when `pending_erasures` is non-empty, stages beside the destination directory (same filesystem as the final path), and **rechecks** ref head (and pending erasures) inside an immediate transaction immediately before inserting the export row (after a successful publish rename). If the head moved, the command fails with “repository changed during export; retry”. Part 2 may extend rechecks (erasure tombstones, hot generation).
- **Merge skip markers.** Section history reads skip decisions from `merge_replay_skips` in the ledger (via `snapshot::History`), never from `.wisp/cache/.../merge-skip.json`.
- **Plaintext copy.** Every HTML page and the CLI success payload include a plaintext-copy warning; the export is not recalled by later erasures (`docs/TRUST-BOUNDARY.md`).
- **Renderer split.** `wisp-engine` collects a redacted `SiteModel`; `wisp-html` renders files only. Page filenames are opaque ids (26-character ULIDs), not paths or titles.
